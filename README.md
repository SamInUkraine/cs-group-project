## Етап 2. Картки класів

### Клас: Bike

| Що він ЗНАЄ (атрибути) | Що він ВМІЄ (методи) |
|---|---|
| bike_id: int - ід велосипеда | get_price_per_min() - повертає вартість хв оренди велосипеда|
| is_electric: bool - тип велосипеда (True - електричний, False - звичайний) | |
| price_per_min: int - вартість хвилини (2 грн / 5 грн) | |

### Клас: Station

| Що він ЗНАЄ (атрибути) | Що він ВМІЄ (методи) |
|---|---|
| name: str - назва станції | add_bike(bike: Bike) - додає велосипед на станцію |
| bikes: list[Bike] - список велосипедів, що зараз на станції | remove_bike() - видаляє велосипед зі станції |
|  | get_bikes_count() - повертає кількість велосипедів на станції |

### Клас:  Client

| Що він ЗНАЄ (атрибути) | Що він ВМІЄ (методи) |
|---|---|
| name: str — ім'я клієнта | can_pay(amount) — перевіряє, чи вистачає грошей |
| balance: int — баланс клієнта | pay(amount) — списує гроші з балансу |
| current_bike: Bike або None — поточний велосипед | get_balance() — повертає поточний баланс |

### Функції поїздок (`rental.py`)
 
| Що файл ЗНАЄ | Що він ВМІЄ (функції) |
|---|---|
| total_revenue: int — скільки мережа заробила загалом | calc_cost(bike, minutes) — повертає вартість поїздки |
| | take_bike(client, station) — повертає "ok", "already_riding" або "no_bikes" |
| | return_bike(client, station, minutes) — повертає (статус, вартість): "ok", "no_bike" або "not_enough_money" |
| | get_total_revenue() — повертає total_revenue |


**Сценарій «Оля бере електричний велосипед на станції А, катається 20 хвилин і повертає його на станцію Б»:**

| Крок сценарію | Хто відповідає (клас.метод або функція) |
|---|---|
| Оля бере електричний велосипед на станції А | `take_bike(olya, station_a)` -> `station_a.remove_bike()`, велосипед записується в `olya.current_bike` |
| катається 20 хвилин і повертає на станцію Б | `return_bike(olya, station_b, 20)` -> `station_b.add_bike(bike)` |
| рахуємо вартість | `calc_cost(bike, 20)` -> `bike.get_price_per_min()` -> 20 × 5 = 100 грн |
| з її балансу списуються гроші | `olya.pay(100)`, `total_revenue` збільшується на 100 |

## Етап 3. План main() і файли

**Демо-сценарій по кроках:**

1. Створюємо 2 станції: Хрещатик і Поділ;
2. Створюємо 5 велосипедів (3 звичайні, 2 електричні): 2 ставимо на Хрещатик, 3 - на Поділ;
3. Створюємо 2 клієнтівзі своїми балансами: Оля з 300 грн і Петро зі 100 грн;
4. Проводимо поїздки;
5. Петро пробує взяти велосипед на Хрещатику, де їх не залишилось - програма відмовляє
6. Друкуємо баланси клієнтів;
7. Друкуємо звіт адміністратора;
8. Запускаємо 3 перевірки


**Файли і власники:**

## Етап 6. Нова вимога

**Що змінили:**
 
| Файл | Клас / функція | Що саме змінено |
|---|---|---|
| `bike.py` | `Bike.__init__` | додано параметр `charge` (заряд, за замовчуванням 100) |
| `bike.py` | `Bike.is_available()` | новий метод: звичайний велосипед завжди придатний, електричний — лише із зарядом ≥ 20 |
| `bike.py` | `Station.remove_bike()` | тепер видає перший придатний велосипед, а якщо таких немає — `None` |
| `bike.py` | `Station.get_low_charge_bikes()` | новий метод: список велосипедів із низьким зарядом |
| `main.py` | `main()` | велосипеди отримали заряд, оновлено порядок велосипедів і поїздки |
| `main.py` | `ride()` | нове повідомлення «немає придатних велосипедів» |
| `main.py` | `print_report()` | у звіт додано список розряджених велосипедів |
 

**Всього місць у коді змінено:** 7

 
**Чому саме стільки (що в архітектурі допомогло або завадило):** допомогло те, що `take_bike` отримує велосипед лише через `Station.remove_bike()` і не знає, як станція його обирає, — тому правило про заряд вистачило додати в одному місці, а логіка поїздок і оплати залишилась без змін. Завадило правило "один файл — один власник": власник `bike.py` пішов із заняття, тому зміни в цьому файлі вносив Семен.
